GitHub Copilot Code Reviewを実務に入れるかどうかは、次の問いに答えられないと決めにくいです。

- 品質の向上に寄与するか
- レビューコストは減るのか

この記事では、実務で使っている API リポジトリの過去20 PRに対して、公開された Copilot Code Review の行単位コメントを分類し、実務での有効性を評価した結果をまとめます。

## 仮説

調査前の仮説は次の3点でした。

- ロジックバグを見つけるには有効である
- 設計に関する問題は人間が対応する必要がある
- linter の次のフェーズとして機能する

## 方法

対象は実務リポジトリの過去20 PRです。
公開された Copilot Code Review の行単位コメントを収集し、次の分類で評価しました。

| 分類 | 定義 | 判断基準 | 例 |
| --- | --- | --- | --- |
| **Valid defect** | 現在のコードに実際の不具合がある | 想定された利用・運用条件で、誤動作や仕様違反が発生することを具体的に説明できる | null で例外、誤った計算、認可漏れ、正常系でデータ不整合 |
| **Valid risk** | 現時点で不具合とは断定できないが、現実的な条件で問題になるリスクがある | 発生条件と悪影響が具体的で、その条件が現実的に起こり得る | 並行更新による競合、外部 API 失敗時の不整合、リトライによる二重処理 |
| **Useful improvement** | 不具合・リスクではないが、変更する実務的価値がある | 保守性・可読性・テスト容易性・性能などに明確な改善があり、変更コストに見合う | 重複処理の共通化、複雑な条件式の整理、重要箇所のテスト追加 |
| **Low-value** | 指摘自体は間違っていないが、対応する価値が低い | 得られる改善が小さい、過剰防御、極端なケース、プロジェクト上重要でない | 発生可能性が極端に低いケースへの複雑な防御、些細なリファクタリング |
| **False positive** | 指摘の前提・推論・結論が誤っている | コード・仕様・フレームワーク等を確認すると指摘された問題が存在しない | 「null になる」と指摘したが型や事前条件で保証済み、実際には排他制御済み |

分類とは別に、**Actionable** を「指摘を受けて PR 内でコード変更が行われたコメント」と定義しました。
技術的な妥当性と、実際に対応したかは別の軸です。

対応判断のイメージは次のとおりです。

| 指摘 | 分類 | 対応 | 理由 |
| --- | --- | --- | --- |
| null 時に 500 | Valid defect | Fix | 実際に発生可能 |
| 二重リクエストで競合 | Valid risk | Fix | 決済処理なので影響大 |
| 変数名を明確にする | Useful improvement | Skip | 今回の PR では不要 |
| 極端な並行実行への対策 | Low-value | Skip | 複雑性増加が大きい |
| null になる可能性 | False positive | Skip | DB 制約で保証済み |

## 結果

対象20 PRから、行単位コメント180件を収集して分類しました。

| 分類 | 件数 | 全指摘に占める割合 |
| --- | --- | --- |
| Valid defect | 46 | 25.6% |
| Valid risk | 27 | 15.0% |
| Useful improvement | 60 | 33.3% |
| Low-value | 28 | 15.6% |
| False positive | 19 | 10.6% |

主な指標は次のとおりです。

- **Actionable Rate**：137 / 180 = **76.1%**
- **最終残存率**：132 / 180 = **73.3%**（対応した変更が最終マージ時にも残っていたコメントの割合）
- **Defect/Risk Rate**：（Valid defect + Valid risk）= 73件、全指摘の **40.6%**
- **False Positive Rate**：19 / 180 = **10.6%**

Actionable Rate はレビュー中にコード変更へつながった割合であり、最終残存率とは区別します。
Actionable だった137件のうち、最終マージ時にも残っていたのは132件で、132 / 137 ≈ 96.4% でした。

Valid defect、Valid risk、Useful improvement の合計は133件です。
Actionable は137件なので、Low-value の一部にも対応したケースがあります。
分類と Actionable は独立した評価軸になっています。

コード変更につながらなかった指摘は43件でした。
コメント数は PR 間で偏りがあり、件数の多い1 PR が全180件の24.4%を占めました。

## 考察

Valid defect または Valid risk が73件ありました。
実行時の分岐、例外処理、ジョブ起動条件、ファイルや DB の整合性など、linter では扱いにくいコード文脈上の問題を見つける候補として、Copilot Code Review は有効でした。

Actionable Rate が76.1%であるため、この対象では指摘の約4分の3が PR 内の変更につながりました。
False positive は10.6%にとどまり、89.4%は少なくとも何らかの技術的妥当性があると評価されました。

ただし、指摘への対応や最終コードへの残存は、品質が実際に向上したことを直接には示しません。
このデータで評価できるのは「Copilot が出した指摘がどれだけ有用だったか」であり、「Copilot がどれだけ問題を見逃したか」は分かりません。
Precision 側の評価はできますが、Recall 側は評価できません。

Useful improvement が60件で最多でした。
不具合検出だけでなく、テスト、保守性、例外処理の改善提案にも使われていました。

一方で、設計方針、運用上の許容リスク、変更スコープの判断は、コードだけから一意に決められません。
そのため、Copilot Code Review は設計レビューを代替するものではなく、人間が妥当性と優先順位を判断する前提の補助的な一次レビューとして位置付けるのが妥当です。

linter を置き換えるものではありません。
静的解析の後に、コード文脈や変更の影響範囲を確認する追加のレビュー信号としては機能します。

レビューコストについては、43件がコード変更につながらなかったため、確認と仕分けの負荷は発生しています。
レビュー時間を測定していないため、総レビューコストが削減されたとはこのデータだけでは結論付けられません。

実務上の比較に使うなら、次の4指標が扱いやすいです。

1. Actionable Rate（指摘を読むコストに対する効率）
2. False Positive Rate（誤った指摘によるノイズ）
3. Defect/Risk Rate（品質問題を発見できた割合）
4. Final Adoption Rate（最終的に残ったコメントの割合）

加えて、指摘数 / PR も見る必要があります。
平均3件 / PR で Actionable Rate 76% の場合と、平均15件 / PR で Actionable Rate 80% の場合では、人間にとっての使いやすさが違います。

## 限界

この結果をそのまま一般化するわけにはいきません。

- 対象は1リポジトリの指定20 PRであり、PR の種類、Copilot の設定、モデルの更新、開発チームの運用が異なる環境へはそのまま一般化できない
- 集計単位はコメントであり、同じ原因に対する重複指摘や、1つの修正で複数コメントに対応した場合を独立した成果として数えている
- 分類と Actionable の判定は、コメント、レビュー応答、コミット、最終差分をもとにした事後評価である
- 判定者の解釈や、対応した事実に引きずられる評価の偏りを完全には排除できない
- Copilot が見逃した不具合、リリース後の障害率、ロールバック、問い合わせ件数を測る対照群がない

次に確認したいことは次のとおりです。

- 同一原因のコメントを修正単位に統合し、PR 単位の中央値とばらつきも併記する
- Copilot あり・なしの類似 PR で、レビュー開始からマージまでの時間、人間のレビューコメント数、手戻り時間を比較する
- リリース後の不具合、障害、ロールバック、追加修正を追跡し、Actionable な修正が品質に与えた影響を確認する
- 人間のレビューで見つかった問題と比較して見逃しを調べ、設計・仕様判断が必要な指摘は別の評価軸で扱う

## まとめ

この対象では、Copilot Code Review は実務で使える水準でした。

- Actionable Rate 76.1%、False Positive Rate 10.6%、Defect/Risk Rate 40.6%
- linter では拾いにくいコード文脈上の問題を見つける候補として有効だった
- 設計レビューの代替ではなく、妥当性と優先順位を人間が判断する一次レビューとして位置付けるのが妥当である
- レビューコストの削減や見逃し（Recall）は、このデータだけでは結論付けられない

「バグ検出器」として見るか「レビュー支援」として見るかで数字の印象は変わります。
Valid defect だけなら25.6%ですが、Valid risk まで含めれば40.6%、Useful improvement まで含めれば73.9%になります。
今回の用途は後者に近いです。
